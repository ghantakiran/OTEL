# GitOps distribution of compiled collector configuration

The Control Plane **Compiles** the **Fleet**'s **Telemetry Contracts** and commits the result. Existing GitOps tooling (Argo/Flux, ConfigMaps) applies the merged tree to the **Agents** and the **Gateway**. There is no OpAMP server, no push protocol and no control-plane backend: reconfiguring the fleet is a commit plus a normal rollout ([ADR 0006](adr/0006-gitops-config-distribution.md), [ADR 0004](adr/0004-git-native-no-backend.md)).

That makes the review of a **Rollout** the only gate between a Contract change and the fleet — which works only if the diff is small, deterministic and infrequent. Everything below exists to keep it that way.

## The loop

```
Telemetry Contract changes (or a Pipeline Profile does)
        ↓
.github/workflows/gitops-rollout.yml            daily, or on demand
        ↓
otel-guardrail compile-fleet fleet              recompiles in place
        ↓
compiled tree differs from the base branch?
        ↓ yes                                   ↓ no
push gitops/fleet-rollout                       close any open rollout PR
open or update ONE pull request                 write nothing
        ↓
a human reviews and merges
        ↓
GitOps tooling applies the merged tree to the fleet
```

Nothing in the loop merges anything.

## Where things land

```
fleet/contracts/orders-api.yaml     the Telemetry Contract, hand-written
fleet/compiled/orders-api.yaml      its collector configuration, generated
fleet/rollout-manifest.yaml         the Rollout Manifest, generated
```

**One file per service, named for the service.** Not `compiled/<tier>/<service>.yaml`: a Service Tier is a mutable field *inside* the Contract, so promoting a service from tier-3 to tier-1 would move its file — a delete plus an add, which reads in the diff as "this service's configuration was removed" rather than "this service's tier changed". It would also break whatever path selector the GitOps tooling points at. The service name is the one identity that does not move, and it is already the identity all of the service's telemetry is keyed on (`service.name`).

Not a directory per service either: there is one artefact per service today, and the Gateway's configuration (C5) is fleet-wide rather than per-service, so it will sit alongside `compiled/` and not inside it.

The **file name is load-bearing**, not decoration: it decides where the compiled configuration lands and whether a configuration is pruned. So `contracts/orders-api.yaml` must declare `service_name: orders-api`. A file whose name disagrees with the Contract inside it is reported as a failure rather than guessed at.

`fleet/` is a *sample* fleet, kept deliberately separate from `guardrail/examples/`. Everything in `fleet/` is meant to compile; several Contracts in `guardrail/examples/` deliberately violate a Standard so CI can prove the Preflight Guardrail blocks them. Same separation, and same reason, as `guardrail/examples/demo-waivers.yaml` versus the live `guardrail/waivers.yaml`: a fixture that must stay broken and an artefact that must stay correct cannot be the same file.

## Every compiled file says it is generated

```yaml
# Compiled collector configuration for the orders-api Agent — Service Tier tier-1.
#
# Generated by 'otel-guardrail compile-fleet'; do not edit this file, the next
# rollout overwrites it. Change one of its two inputs instead:
#
#   Telemetry Contract: contracts/orders-api.yaml — what this service emits
#   Pipeline Profile: tier-1-critical — how that telemetry ships
```

Somebody will eventually find one of these files and want to change a batch timeout in it. That edit would work until the next Rollout silently reverted it, so the file names both of its real inputs. The Contract is named by its path *inside the Fleet* and never on disk: an absolute path would differ between a laptop and a runner, and the only path a reader can act on is the one in the repo.

## Determinism, and why it is not a nicety

Compiling the same Contracts twice produces **byte-identical** files. No timestamps, no run numbers, no absolute paths, no map-iteration order. A file already correct is not rewritten at all.

This is the property the whole review model rests on. A diff carrying reshuffled keys or a regenerated timestamp buries the one line that actually changed, and a reviewer who has learned that rollout diffs are noise stops reading them — at which point the review gate is gone and nobody noticed. `TestCompilingTheFleetTwiceProducesIdenticalFiles` compiles the same Fleet eleven times in one process, because Go randomises map iteration order per range and a single second run could agree by luck.

## When a Contract does not compile

**It is reported and skipped. The rest of the Fleet still rolls out.**

The alternative — refusing the whole Rollout — means one team naming a Signal `metricks` freezes every other team's configuration change until somebody notices. The blast radius of a broken Contract should be the service that broke it.

What makes that safe rather than silent is three things together:

1. **The skip is committed.** `rollout-manifest.yaml` lists every service in the Fleet under `compiled` or `not_compiled`, with the reason. A diff shows what changed and never what is absent, so without the Manifest a missing service would be invisible. With it, the absence is *in the diff a human reviews before merging*.
2. **The command exits 1.** Same meaning as everywhere else in this CLI: a finding about the input. The run's summary and the pull-request body both name the service and the reason.
3. **Nothing regresses.** A service whose Contract just stopped compiling keeps whatever collector configuration it last compiled to. Deleting it would take a running service's telemetry away over an editing mistake, which is a bigger outage than the mistake. It is frozen at that configuration until the Contract or the Profile is fixed — which is what the Manifest entry is telling you.

A configuration with **no Contract behind it at all** is a different case and *is* pruned: a decommissioned service's config would otherwise be applied forever by tooling that has no idea the Contract is gone. The two cases are told apart by the file name — a Contract that still exists but fails keeps its configuration; a Contract that has been deleted loses it.

Two failures are *not* treated this way, because neither is a statement about one service:

| Failure | What happens | Why |
| --- | --- | --- |
| The Fleet directory has no Contracts at all | exit 2, nothing written | A mistyped path or an incomplete checkout would read as "the fleet is empty", and the next step would prune every collector configuration in the repo and commit it — a fleet-wide outage arriving as a green run. |
| A compiled config is not internally coherent | exit 2, nothing written | That is a bug in the compiler or in a Pipeline Profile, and a Profile is fleet-wide, so it is wrong for every service selecting it. It must not land in `not_compiled` blaming a service. |

### The live example

`fleet/contracts/reporting-worker.yaml` is `tier-2`, and only `tier-1` has a published Pipeline Profile today. So it does not compile, `rollout-manifest.yaml` records why, and `compile-fleet fleet` exits 1. That is the real state of the platform, not a fixture.

It is also deliberately temporary. C2 (#11) publishes the tier-2 and tier-3 Profiles; the moment it lands, that Contract compiles, the scheduled job sees the compiled tree no longer match the Contracts, and opens the pull request that adds `compiled/reporting-worker.yaml`. A Contract left failing here forever would train reviewers to skim past the `not_compiled` section — the same failure as an alert nobody reads.

## Why the cron is not spam

A scheduled job that force-pushes a branch and opens a fresh pull request every morning gets muted, and a muted rollout is worse than none: the diff that was the whole review gate is the thing nobody reads. `.github/scripts/gitops-rollout-pr.sh` keeps **exactly one** pull request in step with the Contracts:

| Situation | What the job does |
| --- | --- |
| Compiled tree changed, no rollout PR open | push the branch, open one |
| Compiled tree changed, rollout PR open and stale | update the branch and the PR body |
| Compiled tree changed, PR already proposes exactly this | **nothing at all** — no push, no edit, no notification |
| Compiled tree already correct, rollout PR open | comment and close it |
| Compiled tree already correct, no PR open | nothing |
| A human's PR happens to carry the `fleet-rollout` label | refuse loudly, touch nothing |
| Two open PRs carry the label | refuse loudly, touch nothing |

The mechanics, each of which is a way for the job to know it has no news:

- **A fixed branch**, `gitops/fleet-rollout`, rebuilt from the base branch each run rather than accumulated onto — so the diff is always "the base branch versus what the Contracts compile to today", never a pile of superseded rollouts.
- **No push when the branch already holds this compiled tree.** Only the `fleet/` paths are compared: the branch being based on an older commit is not news worth a force-push and a notification, whereas a different compiled tree is.
- **No edit when the PR body already says exactly this.** The body is built from the JSON report and from `git diff`, never from the CLI's prose, so rewording terminal output does not rewrite an open pull request. It contains no dates and no run numbers, so an unchanged Rollout produces a byte-identical body.
- **A label plus a marker.** The `fleet-rollout` label is how the job finds its pull request; the `<!-- otel-guardrail:fleet-rollout -->` marker in the body is the second key proving what it found is its own. Without the marker, a human labelling their own PR `fleet-rollout` would have its body replaced by tomorrow's rollout.

This is the same shape as the Waiver-expiry cron ([`docs/waiver-expiry.md`](waiver-expiry.md)), for the same reason.

## Reviewing a rollout

Read it as configuration, because that is what it is. The files are generated and deterministic, so every line in the diff is a real change to what the fleet will run.

1. **`rollout-manifest.yaml` first.** It is the summary: which services are covered, which are not, and why. A service moving from `compiled` to `not_compiled` is the thing to look at hardest — it means that service is now frozen.
2. **Then the `compiled/` diff.** A Contract change should touch exactly one file. A Pipeline Profile change should touch every service in the tiers that select it, and nothing else. Anything wider than that is the interesting question.
3. **Merge.** GitOps tooling applies the merged tree. There is no separate deploy step, and no status back-channel from the collectors — fleet health comes from the telemetry itself (ADR 0006).

## Running it by hand

```
otel-guardrail compile-fleet fleet
```

Writes in place, prints what it did, and exits 0 if every Contract compiled, 1 if some did not, 2 if it could not run. `--profiles <file>` compiles against a different Pipeline Profile set; `--format json` prints the machine-readable report the scheduled job reads.

Then review `git diff -- fleet` and commit it like any other change. Compiling is idempotent, so running it when nothing has changed writes nothing and produces no diff.

To trigger the loop itself, dispatch **Fleet rollout** from the Actions tab.

## Guards in CI

- `gitops-rollout-compile_test.sh` and `gitops-rollout-pr_test.sh` run on every PR. They exercise the cron's two halves — which exit code means "propose nothing", and the open/update/close/do-nothing branching — with `gh` stubbed and a bare git repository in a temp directory. Nothing is ever created on the repository.
- The **fleet-up-to-date** job runs on pull requests only: it recompiles and fails if the committed tree is not what the Contracts compile to. On a pull request the author is changing an input and can recompile in the same change, so the input and its output land together. On master the scheduled job is what closes a gap — a Pipeline Profile merging before the fleet is recompiled leaves master briefly behind, and that is a pull request waiting to be reviewed, not a broken build.

## Adding a service to the Fleet

1. Write `fleet/contracts/<service-name>.yaml`, filed under the service's own name.
2. Run `otel-guardrail compile-fleet fleet` and commit both the Contract and the compiled configuration.

If its Service Tier has no published Pipeline Profile, it will appear under `not_compiled` and no configuration will be produced — which is correct, and resolves when that tier gets a Profile.
